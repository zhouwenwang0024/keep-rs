# 数据流与阻塞问题总结（更详细版）

> 目标：在不丢弃 DLOB 构建更新的前提下，通过“机会搜索层可丢弃/可跳过”策略，
> 解决结构性阻塞与陈旧数据处理问题，并给出可观测性方案。

---

## 0. JIT 定价“drift_mid 偏差”专项分析（详细）

### 0.1 问题重述
用户观察到：`binance_mid` 与链上真实价格接近 `115.85`，但 JIT 计算得到的
`reference_price` 约为 `115.50`，出现约千分之三的偏移。

核心疑问：
1) `drift_mid` 的 `best_bid/best_ask` 是否计算错误？  
2) 是否因为阻塞导致 DLOB 过期？

---

### 0.2 结论摘要
**最可能原因不是“公式错误”，而是 `drift_mid` 使用了“有效价格”。**

JIT 的 `drift_mid` 来源不是“普通盘口最优价”，而是：
> **考虑触发单、浮动单、VAMM fallback 等“有效价格”的最优价**

因此：
- 如果 DLOB 中存在触发单/浮动单/VAMM fallback，`best_bid/best_ask` 可能显著偏离
  你直观的“订单簿最优价”。
- 这会使 `spread` 和 `basis_ema` 偏大，从而拉低 `reference_price`。

---

### 0.3 `best_bid/best_ask` 计算链路（真实实现）

#### 1) JIT 入口
```line
drift_mid = (best_bid.price + best_ask.price) / 2
```
数据来源：
```rust
best_levels_with_makers(...)
```

#### 2) `best_levels_with_makers` 逻辑
```rust
for bid in book.bids_with_price(...) {  // ⚠️ 不是 top_bids
    let price = bid.price;
    if best_bid_price.is_none() { best_bid_price = Some(price); }
    if Some(price) != best_bid_price { break; }
    ...
}
```
同理对 `asks_with_price(...)`。

**关键点**：这里是 `bids_with_price/asks_with_price`，不是 `top_bids/top_asks`。

---

### 0.4 `bids_with_price` / `asks_with_price` 是什么？
它们不是简单排序，而是**“有效价格”选择器**，会在以下来源中挑最优价：

- **固定挂单**（普通限价单）
- **浮动单**（相对 oracle 偏移）
- **触发单**（post-trigger price）
- **VAMM fallback 价格**

伪代码逻辑（高度概括）：
```text
best_bid = max(
  fixed_price,
  floating_price(oracle_diff),
  post_trigger_price(trigger_price),
  vamm_fallback_price(...)
)
```

因此：  
**`best_bid/best_ask` 不是你直观看到的“盘口最优价”，而是“可执行最优价”。**

---

### 0.5 为什么会导致 `drift_mid` 偏差？
假设：
- Binance 中间价约 `115.85`
- DLOB 中出现触发单或浮动单导致 best_bid 变低 / best_ask 变高  
则 `drift_mid` 会偏离真实盘口。

进一步影响：
- `spread = binance_mid - drift_mid` 变大  
- `basis_ema` 变大  
- `reference_price = binance_mid - 0.8 * basis_ema`  
  ⇒ 被明显拉低

---

### 0.6 如何确认是不是这个原因？
**建议直接看一次 `jit trigger` 日志的完整字段：**
- `best_bid / best_ask`
- `drift_mid / binance_mid`
- `basis_ema / spread`
- `dlob_slot`

如果同时满足：
- `drift_mid` 明显偏离 `binance_mid`  
- `basis_ema` 很大  
- `dlob_age_ms` 不高  
→ 基本可以判断是“有效价格偏差”，不是阻塞。


## 1. 背景与现状

### 1.1 当前系统的角色分层
- **入口层**：WebSocket 回调，接收用户/slot/市场/价格等更新  
- **DLOB 层**：基于用户与市场更新构建 DLOB  
- **机会搜索层**：基于 DLOB + 价格/策略，寻找可成交机会  
- **交易构造/发送层**：构建交易并发出

### 1.2 当前数据流概览
1. WebSocket 接收更新  
2. 回调内写入缓存，并触发 DLOB 更新  
3. 回调内触发 `book_tx`  
4. 主循环 `book_rx.recv()` 接收信号  
5. 逐市场串行进行 DLOB 查询、机会搜索、构建交易  

### 1.3 现有关键问题
- **入口与 DLOB 更新耦合**：DLOB 更新在回调内同步执行  
- **串行处理**：市场逐个处理，累计延迟  
- **高波动放大效应**：数据更多、机会更多、计算更重 → 延迟上升  

### 1.4 直接后果
- **处理滞后**：可能处理到几秒前的机会  
- **价格与数据失真风险**：基于过时 DLOB/价格决策  
- **吞吐波动**：高峰期积压、低峰期空闲

### 1.5 关键判断
**问题本质是结构性阻塞，不是容量问题。**
- 增大 channel 只会延迟爆炸  
- 需要“入口非阻塞 + DLOB 不丢弃 + 机会搜索可丢弃”

---

## 2. 目标（可量化）

### 2.1 功能目标
- **DLOB 构建更新不丢弃**（保证完整性）  
- **机会搜索可丢弃/可跳过**（保证新鲜度）  
- **入口不阻塞**（保证数据流通）

### 2.2 性能目标
- 高频输入（5ms 级）下 **无 >2s 积压**  
- WebSocket 回调耗时稳定（无明显长尾）  
- 延迟可定位且可解释

---

## 3. 关键原则（分层策略）

### 3.1 DLOB 层：必须完整
- **不允许丢弃 DLOB 构建更新**  
  DLOB 是“事实层”，必须完整才能保证后续逻辑正确。  

### 3.2 机会搜索层：允许跳过
- **机会搜索是“决策层”**，可牺牲完整性换取新鲜度  
- **同市场若上一次搜索未完成，则直接跳过本次搜索**  
- 机会搜索触发频率与耗时直接决定延迟

---

## 4. 深度重构规划（分层落地）

### A. 入口层：只做轻操作
**目标**：确保回调不阻塞、数据快速进入系统。  
**策略**：
- 回调只做：解析、写入缓存、`try_send`  
- 禁止在回调内执行 DLOB 更新、机会搜索或交易构造  
- 若入口压力过大，优先保证 DLOB 更新进入队列

### B. DLOB 层：异步更新（不丢弃）
**目标**：保证 DLOB 更新完整，同时不阻塞入口。  
**策略**：
- 引入独立的 **DLOB 更新队列/任务**  
- 不允许随意丢弃更新  
- 需要明确更新处理速率与 backlog 监控

### C. 机会搜索层：允许跳过
**目标**：保证新鲜度，避免机会搜索阻塞主循环。  
**策略**：
- **同市场并发限制为 1**  
- 若上次机会搜索未完成，本次直接跳过  
- 可将机会搜索任务放入线程池或 worker  
- 允许丢弃旧的搜索任务，只保留最新触发

### D. 主循环与市场并行化
**目标**：避免全市场串行累积延迟。  
**策略**：
- 按市场并行：`join_all` 或 worker pool  
- 计算密集逻辑用 `spawn_blocking`  
- 限制每市场并发度，防止资源争抢

### E. 交易构造与发送解耦
**目标**：策略计算与发送解耦，避免等待往返。  
**策略**：
- 机会搜索只生成交易意图  
- 构造与发送进入独立 pipeline  
- 发送失败不回堵机会搜索层

### F. 订阅共享与策略融合
**目标**：减少重复订阅与重复计算。  
**策略**：
- 引入 `SharedSubscriptions`  
- filler 与 liquidator 共享订阅与缓存  
- 策略层只消费缓存，不直接订阅

---

## 5. 关键机制建议（“不丢 DLOB，丢搜索”）

### 5.1 机会搜索跳过机制（建议）
- 每个 market 维护 `busy` 标志  
- 如果 `busy=true`，新的搜索信号直接跳过  
- 完成后清除 `busy`，等待下次触发  

### 5.2 DLOB 更新处理原则（不丢弃）
- DLOB 更新进入独立队列，必须被消费完成  
- 不通过“丢弃”来减压  
- 通过并发/批处理/队列监控来控制阻塞

---

## 6. 观测与日志（定位阻塞）

### 6.1 必要日志
- WebSocket 回调耗时（start/end）  
- DLOB 更新耗时（每用户/每 slot）  
- 机会搜索耗时（每 market）  
- 机会搜索跳过次数（每 market）  

### 6.2 必要指标
- DLOB 更新队列长度  
- `book_rx` backlog（如果存在）  
- 机会搜索并发度/队列长度  
- 端到端延迟（触发 → 发送）

---

## 7. 异步与并行化设计细化（建议落地）

### 7.1 任务分层与职责
- **任务 A：WebSocket 回调**  
  只做解析/写缓存/投递信号，禁止重逻辑。  
- **任务 B：DLOB 更新任务**  
  独立消费 DLOB 更新队列，保证更新不丢失。  
- **任务 C：机会搜索调度器**  
  接收 `book_rx` 信号，按 market 分发搜索任务。  
- **任务 D：每市场搜索任务**  
  并发上限=1，未完成则跳过本轮。  
- **任务 E：交易构造/发送**  
  从“交易意图队列”异步构造并发送，不阻塞搜索层。

### 7.2 并行策略（明确哪些可并行）
- **可并行**：不同 market 的机会搜索  
- **可并行**：交易构造（CPU 密集）  
- **需串行**：同 market 的机会搜索（避免重入与重复下单）  
- **需完整**：DLOB 更新队列（保证事实层正确）

### 7.3 异步工具选择（建议）
- **tokio::spawn**：并行搜索任务、发送任务  
- **tokio::task::spawn_blocking**：DLOB 查询/计算密集逻辑  
- **mpsc::channel**：分层队列（DLOB 更新、搜索信号、交易意图）

### 7.4 机会搜索跳过逻辑（具体策略）
- 每 market 维护 `busy` 标志（原子/Mutex）  
- 收到新信号：  
  - 若 `busy=false` → 置 `busy=true`，启动搜索任务  
  - 若 `busy=true` → 直接跳过  
- 任务结束后清除 `busy`  
- 记录跳过次数与持续时长

## 8. 流程图对比（现有 vs 目标）

### 8.1 现有流程图（串行 + 回调阻塞风险）
```
WebSocket 回调
  ├─ 写缓存
  ├─ DLOB 更新（同步，可能慢）
  └─ book_tx
        ↓
   主循环 recv()
        ↓
   for 每个 market（串行）
        ├─ DLOB 查询
        ├─ 机会搜索
        └─ 构建交易 → 发送
```

**问题表现**：
- DLOB 更新阻塞回调  
- 市场串行导致累积延迟  
- 机会搜索与发送互相等待

### 8.2 目标流程图（分层异步 + 搜索可跳过）
```
WebSocket 回调（轻操作）
  ├─ 写缓存
  ├─ 推送 DLOB 更新队列
  └─ 推送 book 信号
        ↓
   DLOB 更新任务（独立消费，必须完整）
        ↓
   机会搜索调度器
        ├─ market A（busy=0 → 执行）
        ├─ market B（busy=1 → 跳过）
        └─ market C（busy=0 → 执行）
              ↓
        交易意图队列
              ↓
        交易构造/发送任务（异步）
```

**目标效果**：
- DLOB 更新不阻塞回调  
- 机会搜索按 market 并行  
- 未完成的市场直接跳过  
- 发送与搜索解耦

---

## 9. 风险与取舍
- **机会搜索跳过**：短期损失机会，换取长期稳定  
- **并行化**：需要处理并发一致性  
- **DLOB 更新必须完整**：不能用丢弃来减压

---

## 10. 验收标准
- 高频（5ms 输入）下：**不出现 >2s 的积压**  
- DLOB 更新不阻塞 WebSocket 回调  
- 延迟分布稳定可解释
